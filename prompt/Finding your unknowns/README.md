## 결론

여기서는 지금까지의 **일반적인 ChatGPT 질문과 Codex·Claude Code 같은 작업형 질문을 모두 포함**해 분석했습니다.

당신의 질문 스타일을 완전히 바꿀 필요는 없습니다. 현재도 다음과 같은 강점이 뚜렷합니다.

* 실제 환경, 버전, 파일, 경로를 구체적으로 제공한다.
* 원하는 결과물이 무엇인지 명확히 말한다.
* 답변을 보고 기준을 점점 구체화한다.
* 초보자 관점의 단계별 설명과 실제 실행 가능성을 중시한다.
* 공식 문서, 출처, 최신 정보를 요구한다.
* 문서 형식, 용어, 출력 구조를 세밀하게 지정한다.

다만 지금까지는 종종 **탐색, 설계, 구현, 검증을 한 질문에서 한꺼번에 요청**했습니다. 그러다 보니 AI가 먼저 큰 결과물을 만들고, 당신이 그것을 본 뒤에야 “내가 원했던 건 이게 아니다”라는 숨은 기준이 드러나는 경우가 있었습니다.

블로그에서 제시하는 핵심은 프롬프트를 더 길게 만드는 것이 아닙니다. 프롬프트와 컨텍스트를 작업의 **지도**, 실제 코드와 현실의 제약을 **영토**로 보고, 그 사이의 빈틈인 unknown을 작업 전·중·후에 반복적으로 발견하자는 방식입니다. ([Claude][1])

따라서 당신에게 가장 적합한 변화는 다음입니다.

> **완성된 답을 바로 요청하는 스타일에서, 현재 단계의 불확실성을 먼저 드러내고 다음 단계의 작은 결과물만 요청하는 스타일로 변경한다.**

---

# 1. 지금까지 당신이 자주 사용한 질문 스타일

## 1. 결과 우선형

대표적인 형태:

> “Splunk에서 외부 파일을 Lookup에 쌓고 주기적으로 갱신하고 싶다. API로 자동화할 수 있는 방법은?”

> “이 코드를 기반으로 다시 분석해서 어떻게 코드를 작성해야 하는지도 설명해.”

목표와 실무 환경은 분명하지만, 한 질문에 다음 과정이 모두 들어갑니다.

* 가능한 방식 조사
* 방식 선택
* 아키텍처 설계
* 코드 작성
* 배포
* 테스트
* 운영 시 고려 사항

이 경우 AI는 아직 결정되지 않은 부분을 추측하면서 전체 답변을 만들어야 합니다.

---

## 2. 답을 본 뒤 기준을 발견하는 반응형

대표적인 형태:

> “아이디어가 너무 별로인 것 같은데 실제 여러 L1 체인의 디앱 중에서 재미있고 구현하기 쉬워 보이는 걸 찾아보고 아이디어를 줘.”

> “지금 만들어 놓은 프롬프트가 너무 장황하지는 않은지 확인해줘.”

이것은 나쁜 방식이 아닙니다. 오히려 당신은 결과를 보고 자신의 기준을 빠르게 발견하는 편입니다.

다만 `재미있는`, `별로인`, `깔끔한`, `좋은`, `똑같은 스타일`과 같은 기준은 처음에는 말로 표현하기 어렵고, 예시를 봤을 때 판단할 수 있습니다. 블로그의 분류로 보면 이런 부분이 **Unknown Knowns**, 즉 자신도 아직 언어화하지 못한 암묵적 기준에 가깝습니다. ([Claude][1])

따라서 처음부터 하나의 완성안을 요구하기보다는 **서로 다른 후보나 프로토타입을 먼저 보여달라고 하는 방식**이 더 잘 맞습니다.

---

## 3. 학습 경로 요청형

대표적인 형태:

> “나는 아직 이 코드와 가이드를 이해하지 못하고 있다.”

> “답변대로 순차적으로 진행할 거고, 내가 완벽하게 이해할 수 있는 수준으로 설명해줘.”

> “1회차부터 4회차까지 총정리해줘. 정리해주는 내용을 이정표로 공부해 나갈 거야.”

당신은 단순 정의보다 다음을 선호합니다.

1. 전체 구조를 먼저 파악한다.
2. 구성 요소의 역할을 이해한다.
3. 실행 흐름을 따라간다.
4. 실제로 직접 실행한다.
5. 결과를 검증한다.

현재 질문에서는 이를 한 번에 모두 설명해달라고 하는 경향이 있습니다. 블로그식으로 바꾸면 먼저 **내가 무엇을 모르는지도 모르는 상태인지 확인하고**, 전체 지도를 만든 다음 세부 학습으로 들어가게 됩니다.

---

## 4. 레퍼런스 기반 요청형

대표적인 형태:

> “이 웹사이트 스타일이 너무 마음에 들어. 이거와 똑같은 스타일로 웹사이트를 만들 거야.”

> “이 프로젝트에 있는 스타일대로 문서를 만들고자 한다.”

> “기존 파일의 형식과 톤을 참고해서 새 항목을 만들어줘.”

당신은 추상적인 설명보다 실제 사례를 기준으로 결과물을 맞추는 것을 선호합니다. 이것은 블로그가 권하는 `References` 방식과 매우 잘 맞습니다.

블로그에서도 원하는 바를 직접 설명하기 어렵다면 코드, 문서, 디자인 같은 레퍼런스를 제공하고, 에이전트가 그 구조와 의미를 읽게 하는 방식을 권합니다. 특히 코드 작업에서는 스크린샷보다 실제 소스가 더 풍부한 기준이 될 수 있다고 설명합니다. ([Claude][1])

다만 지금까지는 종종 “이것과 똑같이”라고만 요청했습니다. 앞으로는 **레퍼런스의 어떤 특성을 가져오고 무엇은 가져오지 않을지**를 먼저 분해하게 하는 편이 좋습니다.

---

## 5. 공식 자료 검증형

대표적인 형태:

> “출처 가져와봐.”

> “실제로 공식 문서에서 어떻게 말하는지 확인해줘.”

> “현재 가격과 제한을 찾아봐.”

> “다른 API도 제공하는지 확인해줘.”

당신은 단순한 일반 지식보다 다음을 중요하게 생각합니다.

* 현재 버전에 맞는 정보
* 공식 문서
* 실제 요금과 제한
* 운영 환경에서의 적용 가능성
* 추측과 검증된 사실의 구분

이 유형은 이미 좋은 질문 방식입니다. 다만 앞으로는 “찾아봐”에서 끝내지 않고, **현재 알고 있는 것과 아직 확인해야 할 것을 먼저 분리**하면 조사 결과가 더 의사결정 중심으로 바뀝니다.

---

## 6. 출력 형식 통제형

대표적인 형태:

> “HTML로 출력해줘.”

> “Markdown만 출력하고 설명은 빼줘.”

> “하나의 JSON 객체만 반환해.”

> “PDF 파일로 만들어줘.”

> “내용을 바꾸지 말고 문장만 정리해줘.”

당신은 결과물이 어디에 사용되는지를 알고 있기 때문에 출력 형식을 구체적으로 지정합니다. 이것은 명확한 **Known Known**이므로 그대로 유지하는 것이 좋습니다.

이런 작업까지 사분면 분석이나 사각지대 점검을 적용할 필요는 없습니다.

---

## 7. 프롬프트 제품화형

대표적인 형태:

> “이 방법을 프롬프트로 만들어줘.”

> “Codex exec 형태로 전달할 거야.”

> “기존에 요청했던 스타일을 범용 프롬프트로 바꿔줘.”

> “GPTs 앱용 프롬프트로 통합해줘.”

당신은 일회성 답변보다 반복해서 사용할 수 있는 작업 규칙을 만들려는 경향이 강합니다.

다만 여기서 모든 상황을 하나의 거대한 프롬프트에 미리 넣으려고 하면, 블로그가 지적하는 것처럼 너무 구체적이어서 필요한 방향 전환을 막거나, 반대로 추상적인 규칙만 많아질 수 있습니다. 블로그는 지나치게 구체적인 지시와 지나치게 모호한 지시 모두 문제가 되며, 현재 사고 단계와 경험 수준을 알려주는 것이 중요하다고 설명합니다. ([Claude][1])

# 2. 당신의 질문을 네 종류의 Unknown으로 보면

블로그는 작업에서 생기는 불확실성을 네 종류로 나눕니다. ([Claude][1])

| 상태                   | 당신의 질문에서 나타나는 형태                          | 적합한 질문 방식      |
| -------------------- | ----------------------------------------- | -------------- |
| **Known Knowns**     | Splunk 9.4.12, 특정 파일 경로, HTML 출력, 트랜잭션 필수 | 바로 작업 요청       |
| **Known Unknowns**   | “SHC끼리 자동 동기화되는가?”, “API 가격이 얼마인가?”       | 조사 또는 인터뷰      |
| **Unknown Knowns**   | “재미있는 디앱”, “깔끔한 디자인”, “이 사이트 같은 느낌”       | 여러 후보·프로토타입 제시 |
| **Unknown Unknowns** | 처음 다루는 코드베이스, 생소한 제품, 숨은 운영 리스크           | 사각지대 점검        |

중요한 점은 **질문마다 네 가지를 모두 작성할 필요가 없다는 것**입니다.

블로그의 사분면은 매번 표를 작성하기 위한 출력 형식이라기보다, 현재 어떤 대화 방식이 필요한지를 판단하기 위한 진단 도구에 가깝습니다. 제가 읽은 블로그의 의도는 다음과 같습니다.

* 모르는 것도 모르면 → 사각지대 점검
* 보면 판단할 수 있으면 → 후보나 프로토타입
* 결정하지 못한 사항을 알고 있으면 → 인터뷰나 조사
* 충분히 결정됐으면 → 구현 계획
* 구현 중 예상 밖 상황이 나오면 → 구현 기록
* 완료 후 이해가 부족하면 → 설명 문서와 퀴즈

블로그도 구현 전에는 사각지대 점검, 브레인스토밍·프로토타입, 인터뷰, 레퍼런스, 구현 계획을 사용하고, 구현 중에는 결정 기록을 남기며, 완료 후에는 설명 자료와 퀴즈를 사용하는 흐름을 제시합니다. ([Claude][1])

# 3. 앞으로 사용할 기본 질문 구조

당신에게 가장 잘 맞는 기본형은 다음입니다.

```text
나는 [달성하려는 목표]를 하려고 한다.

현재 위치:
- 내가 가진 경험 또는 현재 진행 단계
- 이미 확정한 사실과 제약

아직 모르거나 결정하지 못한 것:
- 현재 인식하고 있는 불확실성

지금은 [사각지대 점검 / 후보 탐색 / 인터뷰 / 계획 / 구현 / 검증] 단계다.

[이번 단계에서 필요한 작업]만 해줘.
아직 [다음 단계의 작업]은 하지 마.

결과는 [원하는 형식]으로 정리해줘.
```

항상 모든 항목을 채울 필요는 없습니다. 핵심은 다음 세 가지입니다.

1. **내가 지금 어디까지 생각했는지**
2. **무엇을 알고 무엇을 모르는지**
3. **이번 응답에서 어디까지만 진행할지**

# 4. 기존 질문을 블로그 스타일로 변환한 예시

## 유형 1. 처음 접하는 기술을 배우는 질문

### 기존 스타일

> “Groq 이거 무슨 서비스야? 어떻게 사용하는 건데?”

### 변경된 스타일

```text
나는 보안 자동화 개발 경험은 있지만 LLM inference infrastructure는 익숙하지 않다.

Groq가 무엇인지 배우는 것 자체보다, 실제 업무에서 사용할 가치가 있는지 판단하고 싶다.

바로 사용 방법부터 설명하지 말고 먼저 사각지대 점검을 해줘.

다음을 중심으로 내가 아직 질문할 줄도 모르는 부분을 알려줘.

- 먼저 알아야 할 핵심 개념
- 다른 LLM 서비스와 비교해야 할 기준
- 사용 전에 알아야 할 제약
- 초보자가 흔히 오해하는 부분
- 다음 단계에서 내가 결정해야 할 사항

아직 설치 방법이나 코드는 작성하지 마.
```

### 변화한 점

기존에는 AI가 임의로 설명 범위를 정했습니다. 변경된 질문에서는 현재 경험 수준과 판단 목적을 알려주고, 먼저 관련 지형을 파악하게 합니다.

## 유형 2. 첨부한 코드와 문서를 이해하는 질문

### 기존 스타일

> “나는 아직 이 코드와 가이드를 이해하지 못하고 있다. 단계별로 내가 완벽하게 이해할 수 있게 설명해줘.”

### 변경된 스타일

```text
첨부한 Splunk Lookup 설정 가이드와 Python 파일들을 이해하려고 한다.

나는 Splunk 운영 경험은 있지만, 이 코드에서 사용하는 Splunk 전용 Python 구조와 인증 처리 방식은 익숙하지 않다.

현재 알고 있는 것은 다음과 같다.

- 외부 API에서 데이터를 받아온다.
- 데이터를 CSV Lookup 형태로 저장한다.
- 작업이 주기적으로 실행되어야 한다.

먼저 첨부 파일 전체를 살펴보고 사각지대 점검을 해줘.

그다음 아래 내용만 설명해줘.

1. 각 파일의 역할
2. 파일 사이의 호출 관계
3. 인증 정보가 전달되는 흐름
4. 외부 API 데이터가 Lookup이 되는 흐름
5. 내가 코드를 수정하기 전에 반드시 알아야 할 개념

아직 코드 수정안이나 배포 절차는 작성하지 마.
불확실한 부분은 추측하지 말고 따로 표시해줘.
```

### 다음 질문

```text
방금 만든 전체 흐름을 기준으로 첫 번째 파일부터 공부하자.

한 번에 한 파일만 설명해줘.
먼저 settings.py가 전체 구조에서 어떤 역할을 하는지 설명하고,
내가 이해했는지 확인하는 질문을 마지막에 하나만 해줘.
```

당신은 한 번에 모든 설명을 읽는 것보다 실제로 순차적으로 학습하려는 목적이 있으므로, 이처럼 **전체 지도와 세부 학습을 분리**하는 것이 더 적합합니다.

## 유형 3. 구현 방법과 아키텍처를 결정하는 질문

### 기존 스타일

> “외부 Python 프로그램 + cron + SCP + Splunk REST API 방식으로 구현하는 방법을 자세히 설명해줘. REST API에 전달하면 클러스터끼리 알아서 맞춰지는 거야?”

### 변경된 스타일

```text
Splunk 앱 내부에서 API를 호출하지 않고,
외부 Python 프로그램이 CSV를 생성한 뒤 Splunk Lookup을 갱신하는 구조를 검토하고 있다.

현재 확정한 것은 다음과 같다.

- Splunk Enterprise 9.4.12를 사용한다.
- Search Head Cluster 환경이다.
- 외부 Python 프로그램과 주기 실행 방식을 사용하려 한다.
- 자격 증명은 평문 파일에 저장하지 않는다.

아직 결정하지 못한 것은 다음과 같다.

- 어느 Search Head로 요청해야 하는가
- Lookup 파일이 클러스터에 어떻게 복제되는가
- app namespace를 어디로 지정해야 하는가
- 실패했을 때 이전 Lookup을 어떻게 보존할 것인가
- 운영 배포 전에 어떻게 테스트할 것인가

먼저 현재 구성과 공식 문서를 기준으로 검토해줘.

그다음 나를 한 번에 한 질문씩 인터뷰해줘.
내 답변에 따라 아키텍처, 보안 또는 운영 방식이 바뀌는 질문을 우선해줘.

아직 코드나 최종 구축 절차는 작성하지 마.
```

블로그도 남은 모호성을 확인할 때 한 번에 하나씩 질문하고, 답변에 따라 아키텍처가 달라질 수 있는 질문을 우선하라고 제안합니다. ([Claude][1])

### 인터뷰가 끝난 뒤 사용할 질문

```text
지금까지 확인한 내용을 기반으로 구현 계획을 작성해줘.

다음 순서로 정리해줘.

1. 아직 내가 변경할 가능성이 높은 결정
2. 최종 아키텍처와 데이터 흐름
3. 인증과 권한 처리
4. 실패 및 롤백 처리
5. 테스트 방법
6. 실제 구현 순서
7. 단순한 파일 작성이나 반복 작업

아직 코드는 작성하지 마.
```

블로그에서도 계획을 작성할 때 기계적인 작업보다 데이터 모델, 인터페이스, 사용자 흐름처럼 변경될 가능성이 높은 결정을 앞에 배치하는 방식을 권합니다. ([Claude][1])

## 유형 4. 아이디어를 찾는 질문

### 기존 스타일

> “초보자가 만들기 적절한 수준의 재미있는 Arc 디앱 아이디어를 줘. 한국인의 특성이 들어가면 좋겠고 반드시 트랜잭션이 동작해야 한다.”

### 변경된 스타일

```text
Arc 테스트넷에서 초보자가 구현할 수 있는 디앱을 만들려고 한다.

확정된 조건은 다음과 같다.

- 단순 조회 서비스가 아니라 실제 트랜잭션이 발생해야 한다.
- 한국 사용자가 보고 재미를 느낄 만한 요소가 있어야 한다.
- 혼자서 MVP를 구현할 수 있어야 한다.
- 테스트넷 데모로 직접 보여줄 수 있어야 한다.

다만 내가 말하는 ‘재미있는 아이디어’의 기준은 아직 정확히 설명하기 어렵다.
여러 사례를 보면 어떤 방향이 마음에 드는지는 판단할 수 있다.

기존 여러 L1 체인에서 실제로 만들어진 간단한 디앱 사례를 참고해서,
서로 성격이 크게 다른 6가지 방향을 제안해줘.

각 방향은 다음만 보여줘.

- 사용자가 30초 동안 경험하는 흐름
- 왜 블록체인 트랜잭션이 필요한지
- 한국적인 요소
- MVP 구현 난이도
- 비슷한 기존 사례와 차별점

아직 상세 기능이나 아키텍처는 작성하지 마.
내 반응을 보고 아이디어 기준을 좁히는 것이 이번 단계의 목표다.
```

이 방식은 AI에게 “가장 좋은 아이디어 하나”를 추측하게 하지 않습니다. 서로 다른 후보를 제시하고, 당신이 반응하면서 암묵적인 취향을 언어화하도록 만듭니다.

블로그도 디자인이나 기능의 기준을 말로 설명하기 어려운 경우, 실제 구현 전에 여러 방향의 프로토타입을 만들어 반응하는 방식을 권합니다. ([Claude][1])

## 유형 5. 좋아하는 웹사이트를 레퍼런스로 사용하는 질문

### 기존 스타일

> “이 웹사이트 스타일이 너무 마음에 들어. 이거와 똑같은 스타일로 웹사이트를 만들 거야. 어떤 스타일인지 자세하게 분석해줘.”

### 변경된 스타일

```text
이 웹사이트를 새 사이트의 디자인 레퍼런스로 사용하려고 한다.

나는 이 사이트가 마음에 들지만,
정확히 어떤 요소 때문에 좋아하는지는 아직 언어화하지 못했다.

먼저 레퍼런스를 다음 기준으로 분해해줘.

- 콘텐츠 계층 구조
- 레이아웃과 여백
- Typography
- 색상과 대비
- 카드 및 테이블 표현
- 내비게이션 방식
- 상호작용과 애니메이션
- 전체적으로 느껴지는 분위기

각 요소에 대해 다음을 구분해줘.

1. 이 사이트의 정체성을 만드는 핵심 요소
2. 없어도 되는 부가 요소
3. 그대로 가져오면 부자연스러울 수 있는 요소
4. 내 사이트에 맞게 재해석해야 할 요소

분석이 끝나면 백엔드 연결 없이,
가짜 데이터를 사용한 단일 HTML 파일로 서로 다른 3가지 방향을 만들어줘.

실제 애플리케이션 코드는 아직 수정하지 마.
```

기존의 “똑같이 만들어줘”보다 훨씬 좋은 방식입니다. 레퍼런스를 복제 대상으로 보지 않고, 당신의 숨은 취향을 발견하기 위한 도구로 사용합니다.

## 유형 6. 최신 정보와 비용을 조사하는 질문

### 기존 스타일

> “X API 가격 얼마야?”

> “수백~수천 명의 계정을 계속 크롤링하려는 것.”

### 변경된 스타일

```text
수백 명에서 수천 명의 X 계정 게시물을 지속적으로 수집하는 시스템을 검토하고 있다.

최종 목표는 단순히 X API 가격을 아는 것이 아니라,
이 방식이 운영 가능한지 결정하는 것이다.

현재 확인해야 한다고 생각하는 것은 다음과 같다.

- 현재 API 요금
- 게시물 조회 Endpoint
- Rate limit
- 사용자 단위인지 앱 단위인지
- 월간 예상 요청량과 비용

하지만 장기 운영, 정책, 계정 제한과 관련해서는
내가 무엇을 추가로 확인해야 하는지 잘 모른다.

먼저 이 수집 방식에 대한 사각지대 점검을 해줘.

그다음 현재 공식 문서를 우선으로 조사해서 다음을 구분해줘.

1. 공식적으로 확인된 사실
2. 문서에 명확히 나오지 않는 부분
3. 계산을 위해 사용한 가정
4. 정책 또는 운영상 위험
5. 현실적으로 선택 가능한 대안

아직 구현 코드는 작성하지 말고,
의사결정 문서 형태로 정리해줘.
```

이제 질문의 중심이 단순 가격 조회에서 **운영 가능성에 관한 의사결정**으로 바뀝니다.

## 유형 7. 보안 분석 결과를 판단하는 질문

### 기존 스타일

> “이 파일이 일부 백신에서는 악성으로 탐지되는데 실제 실행 흐름에서는 악성 행위가 보이지 않는다. 오탐 가능성이 높은 것으로 정리해줘.”

### 변경된 스타일

```text
특정 파일에 대한 백신 탐지 결과를 검토하고 있다.

현재 확보한 정보는 다음과 같다.

- 일부 백신에서 암호화 또는 난독화 관련 기능으로 탐지한다.
- 공식 배포처에서 제공하는 파일이다.
- 약 한 달 전부터 유사한 탐지 이슈가 보고되었다.
- 현재까지 확인한 실행 흐름에서는 명확한 악성 행위가 보이지 않았다.

다만 정상 파일이라고 단정하기에는 아직 검증되지 않은 부분이 있을 수 있다.

바로 최종 안내문을 작성하지 말고 먼저 다음을 구분해줘.

1. 검증된 사실
2. 현재 분석에 사용한 가정
3. 아직 확인되지 않은 사항
4. 결론을 뒤집을 수 있는 추가 증거
5. 최소한으로 추가 확인해야 할 항목

그다음 현재 증거 수준을 넘어서 단정하지 않는 표현으로
사용자 안내문을 작성해줘.
```

이 방식은 보안 판단에서 특히 유용합니다. AI가 그럴듯한 결론을 먼저 만드는 것을 막고, 결론의 근거와 빈틈을 먼저 드러냅니다.

## 유형 8. 단순 문장 교정

### 기존 스타일

> “내용 바꾸지 말고 문장만 정리해줘.”

이 질문은 이미 충분히 좋습니다. 오히려 다음 정도만 명확히 하면 됩니다.

```text
아래 문장의 의미, 사실관계, 판단 강도는 바꾸지 말고
어색한 문장과 문단 연결만 자연스럽게 정리해줘.

새로운 정보나 근거는 추가하지 마.
결과만 출력해줘.
```

이 작업은 결과와 기준이 모두 확실한 **Known Known**입니다. 사각지대 점검이나 인터뷰를 추가하면 질문만 불필요하게 길어집니다.

Ubuntu 명령어, 맞춤법, 단순 번역, 짧은 문장 정리와 같은 작업도 지금처럼 바로 질문하는 편이 좋습니다.

```text
- 완료 후 설명과 검증

각 프롬프트에는 사용 시점, 필요한 입력, 예상 출력과 종료 조건만 포함해줘.
```

# 5. 당신에게 맞는 단계별 짧은 프롬프트 모음

## ① 처음 다루는 영역: 사각지대 점검

```text
나는 [목표]를 하려고 한다.

현재 [관련 경험]은 있지만,
[익숙하지 않은 영역]은 잘 모른다.

내가 현재 알고 있는 것은 [알고 있는 사실]이다.

바로 해결안을 만들지 말고,
먼저 이 작업에 대한 사각지대 점검을 해줘.

내가 질문할 줄도 모르는 중요한 사항,
좋은 결과의 기준,
흔한 실패 지점,
먼저 확인해야 할 전제조건을 알려줘.
```

---

## ② 취향이나 기준을 설명하기 어려울 때: 후보 탐색

```text
나는 원하는 결과를 보면 판단할 수 있지만,
아직 그 기준을 정확하게 설명하지 못한다.

[목표와 고정 조건]을 기준으로
서로 성격이 크게 다른 [3~6]가지 방향을 보여줘.

완성안을 만들지 말고,
내가 반응하며 기준을 좁힐 수 있을 정도의
작은 예시나 프로토타입만 만들어줘.
```

```text
지금까지의 컨텍스트를 기준으로

한 번에 한 질문만 해줘.

- 보안

- 비용
```

## ⑥ 실제 구현: 결정 기록

```text
승인된 계획을 기준으로 구현해줘.

구현 중 예상하지 못한 제약이나 Edge case가 발견되면
보수적인 방식을 선택하고 계속 진행해줘.

다만 다음 내용을 implementation-notes.md에 기록해줘.

- 발견한 문제
- 원래 계획과 달라진 부분
- 선택한 대응 방식
- 그 방식을 선택한 이유
- 나중에 다시 검토해야 할 사항
```

블로그도 계획과 달라질 수밖에 없는 상황이 생기면 구현 기록 파일에 변경 사항과 이유를 남기는 방식을 제안합니다. ([Claude][1])

## ⑦ 작업 완료 후: 설명과 이해 확인

```text
완료된 작업을 내가 직접 검토하고 운영할 수 있도록 설명해줘.

다음을 포함해줘.

- 무엇이 변경되었는가
- 왜 이렇게 구현했는가
- 전체 동작 흐름
- 기존 방식과 달라진 점
- 주요 제약과 Trade-off
- 남아 있는 위험
- 문제가 발생했을 때 확인할 위치

마지막에는 내가 내용을 제대로 이해했는지 확인하는 퀴즈를 만들어줘.
정답은 바로 보여주지 마.
```

블로그 역시 구현 후 코드 변경만 보는 것으로는 전체 동작을 이해하기 어려울 수 있으므로, 설명 자료와 퀴즈를 통해 이해도를 확인하는 방식을 제안합니다. ([Claude][1])

# 6. 앞으로 유지할 것과 바꿀 것

## 그대로 유지할 것

* 지금처럼 자연스럽고 직설적인 말투
* 버전, 파일 경로, 서버 역할 같은 구체적인 환경 정보
* 실제 목적과 사용처
* 공식 문서와 출처 요구
* 원하는 출력 형식
* “내용을 바꾸지 마”, “결과만 출력해” 같은 명확한 제한
* 답변을 보고 솔직하게 피드백하는 방식

## 바꿀 것

### 기존

```text
이걸 분석하고,
가장 좋은 방식을 찾아서,
구현 방법을 설명하고,
코드도 작성하고,
테스트 방법과 운영 시 주의 사항까지 알려줘.
```

### 변경

```text
나는 지금 이 문제를 처음 검토하는 단계다.

현재 알고 있는 것과 모르는 것은 다음과 같다.

먼저 사각지대 점검만 해줘.
아직 방식 선택이나 구현은 하지 마.
```

그다음:

```text
이제 남아 있는 결정 사항을
중요한 순서대로 한 번에 하나씩 질문해줘.
```

그다음:

```text
지금까지 결정된 내용으로 구현 계획을 작성해줘.
변경 가능성이 높은 결정을 앞에 보여줘.
```

그다음:

```text
승인된 계획대로 구현하고,
계획에서 달라진 부분은 implementation-notes.md에 기록해줘.
```

# 최종적으로 바뀌어야 하는 당신의 질문 문법

당신의 기존 질문 문법은 대체로 다음과 같았습니다.

> **상황 설명 → 원하는 최종 결과 → 자세히 전부 해줘**

앞으로는 다음 문법이 가장 잘 맞습니다.

> **현재 위치 → 알고 있는 것 → 아직 모르는 것 → 이번 단계에서만 필요한 작업 → 아직 하지 말아야 할 작업**

이를 가장 짧게 표현하면 다음과 같습니다.

```text
나는 [목표]를 하려고 하고 현재 [단계]에 있다.

[이 부분]은 알고 있지만,
[이 부분]은 아직 모르거나 결정하지 못했다.

지금은 [사각지대 점검 / 후보 탐색 / 인터뷰 / 계획 / 구현 / 검증]만 해줘.
아직 다음 단계로 넘어가지는 마.
```

핵심은 **더 긴 프롬프트를 쓰는 것이 아니라, AI에게 지금 어느 단계에 있으며 무엇을 아직 추측하면 안 되는지를 알려주는 것**입니다.
